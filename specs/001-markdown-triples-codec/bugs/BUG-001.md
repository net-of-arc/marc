# Bug Report: Text values are blobs, inline labels are ignored, and order is lexicographic instead of natural

**Type**: Spec gap (Issues 1, 2, 4); the spec mandates the wrong behaviour (Issue 3, a requirement change against FR-007/FR-018)
**Severity**: High (the decoded bag misrepresents prose structure and order for every multi-paragraph node; the fix changes the public iteration contract and the canonical file layout)
**Feature**: 001-markdown-triples-codec
**Reported**: 2026-10-24
**Status**: Resolved
**Patched**: 2026-10-24
**Implemented**: 2026-10-24 — Phase 9 (T088–T099), `go test -race ./...` green

## Description

There are four related defects in how the codec handles text values and order. They were reproduced on the current tree with a probe node (`tags: [zeta, alpha]`, two default paragraphs, a `**Note**: …` paragraph, an inline typed edge, and an edge block written `replaces` before `conformsTo`):

```text
conformsTo "[[B]]"
replaces   "[[Z]]"
supports   "[[RFC 8446]]"
tags       "alpha"
tags       "zeta"
text       "abc [[A]]\n\ndef\n\n**Note**: This is a note.\n\nSee [supports:: [[RFC 8446]]] here."
```

### Issue 1: Multi-paragraph text decodes as one blob

```markdown
abc

def
```

**Observed**: one `text` triple, `"abc\n\ndef"`.
**Expected**: two `text` triples, `"abc"` and `"def"`, one per paragraph, in document order. This applies to every non-`Many` text-role predicate: the default text and labelled text alike. Equal paragraphs still collapse to one value (set semantics, FR-006; CORE §8.4 `append`: "every paragraph not yet present").

### Issue 2: An inline bold label is not recognised

**Observed**: `**Note**: This is a note.` stays inside the default text blob. Only a `**Label**` alone on its line is a label.
**Expected** (clarified): a paragraph that starts with `**Label**:` decodes as a value of the label's predicate (`note` → `"This is a note."`), the same way a `**Label**` line followed by a paragraph does.
- **Only the colon form counts.** `**Note** This is a note` (no colon) stays prose, because at the start of a paragraph it can't be told apart from emphasis.
- **The decoder does not consult the schema** for this decision. Label → predicate resolution itself is unchanged: schema when configured, otherwise camelCase join.
- **The encoder keeps writing the CORE §4 form** (`**Label**` on its own line, then the paragraph). The colon form is tolerant-reader input only, and byte identity is not required for it.

### Issue 3: Order is lexicographic, not natural

**Observed**: `Triples()`, `Predicates()` and `Values()` and the encoder all sort predicates by code point and values by canonical rendering. `tags: [zeta, alpha]` becomes `[alpha, zeta]`, and an edge block written `replaces, conformsTo` is re-emitted as `conformsTo, replaces`.
**Expected** (clarified):
- **Decoder (Markdown → triples)**: iterators yield triples in **document order**. The CORE §4 section order (meta → text → edge → link) holds, because that is the order the file is written in. Within each section, predicates and their values appear in the order they occur in the file.
- **Encoder (triples → Markdown)**: the CORE §4 section layout is mandatory and unchanged. **Within** each section, predicates and their values are written in the order the application added the triples to the bag (`NewNode` insertion order; for a decoded node, document order).
- **Set semantics stay in place**: a duplicate triple is dropped, and the first occurrence fixes its position.
- **This does not violate CORE §3.** CORE says the written order "carries no meaning" and that a producer "SHOULD write them in a stable order". Insertion order is stable, and lexicographic order is only one SHOULD-level suggestion. Determinism becomes "equal bags built in the same order encode identically" instead of "equal bags encode identically".

### Issue 4: Untyped links inside text are not exposed

**Observed**: `[[A]]` in prose is reachable only by re-parsing the `Text` value. The inline typed form `[supports:: [[RFC 8446]]]` already decodes as a triple (R9, T057). That works correctly and must be kept.
**Expected** (clarified):
- **Untyped links** (`[[Target]]` and `[[Target|text]]`, CORE §7) found inside text values are exposed through a **derived, read-only view** on `Node`: for each text predicate, the `Ref`s found in its values, in document order.
- **They are not triples.** CORE §3 and §4 say "untyped links … produce no triple of their own". No `@link` predicate is introduced.
- **Encoding needs no change**: the links live in the prose and are written with it.
- **Markdown `[text](url)` links are out of scope.**

## Root Cause Analysis

The root cause is a spec oversight, carried forward by an explicit research decision. It is not implementation drift: the code does what the artifacts say.

- **Issues 1 and 3 share a root.** The spec copied CORE's SHOULD-level "lexicographic" suggestion (§3, §8.5) into MUSTs (FR-007, FR-018, AS 2.2). Once values were sorted, paragraph order could no longer survive as separate values. R8 therefore folded all paragraphs into one `Text` so that their order would be preserved. Moving to insertion-ordered sets removes the reason for the blob.
- **Issue 2** is a tolerant-reader gap. CORE §4 shows only the own-line label, and format.md §5 lists every non-canonical form accepted except this one.
- **Issue 4** comes from correctly applying CORE's "untyped links produce no triple" (FR-011) without offering any other way to reach those links. The spec treated "not a triple" as "not exposed".
